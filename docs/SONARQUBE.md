# SonarQube Community in GitHub Actions

The `SonarQube quality` workflow runs on pushes, pull requests and manual dispatch. It uses Java 21, SonarQube Community Build `26.9.0.129388-community` and SonarScanner for Maven `5.8.0.7211`.

## How it works

1. Start a disposable SonarQube server exposed only on the runner's loopback interface. Elasticsearch checks remain enabled; required Linux limits are configured.
2. Wait for readiness, replace the new server's default admin password with a random value, create the project and generate a masked token. No external Sonar account, repository secret or paid subscription is needed.
3. Build and run the default Maven unit/integration suite as selected by the repository's default profile, producing JaCoCo reports. Dedicated container, performance and browser suites remain in their existing workflows; this job does not claim to replace them.
4. Analyse Java and supported non-JVM repository files with Maven's `scanAll` option. Generated files, dependency directories, frontend test fixtures and browser output are excluded. The Maven scanner derives Java modules and test roots from their POMs. Frontend dependencies are installed if `web-ui/package-lock.json` exists. Frontend coverage is not generated by this workflow.
5. Wait for the default Quality Gate. A failing gate fails the job; it is not ignored.
6. Export measures, issues, hotspots and gate status, upload reports, and destroy the server even after failure.

## Viewing results

Open **Actions > SonarQube quality > the run**. Read the job summary and download the **sonarqube-report** artifact. It includes:

- `quality-gate.json`: the gate status and evaluated conditions.
- `measures.json`: available code size, coverage, duplication and rating metrics.
- `issues.json` and `hotspots.json`: the first 500 entries, with API pagination/total information.
- `SUMMARY.md`, server diagnostics, JaCoCo and JUnit reports.

Security hotspots require human review. A successful analysis or Quality Gate is not evidence that all vulnerabilities have been eliminated. CodeQL, dependency scans, secret scans and application security tests remain separate controls.

## Limits and persistent deployment

The server uses its embedded evaluation database and exists only for one job. There is no live dashboard after cleanup, cross-run issue history, established new-code baseline, PR decoration or branch history. A fresh project's default gate may not measure the same new-code changes as a persistent project. Review overall measures and findings rather than interpreting the first gate as complete acceptance. Artifacts are retained for 14 days; reports are truncated to the first 500 issues/hotspots.

For a permanent dashboard and baseline, deploy a persistent SonarQube server with PostgreSQL/TLS/backups or connect SonarQube Cloud. That requires its URL, project key, credentials and appropriate service access.

This CI server is not a production SonarQube deployment. All generated credentials expire with the container. Avoid printing them or adding them to artifacts.
